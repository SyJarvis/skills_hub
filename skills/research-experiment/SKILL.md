# 研究运行管理

在本工作区中，“实验”首先指一次具体、可追溯的代码运行，例如训练、评测、基准测试、
消融或调试。除非研究问题本身要求，普通运行不必先建立研究假设，也不强制归入多级
实验体系；若用户明确采用科学实验设计，则应保留其变量、对照和判定标准。

## 最小记录

每次具有独立意义的执行或重跑使用单独目录。优先遵循项目已有的结果存放约定；只有工作区集中管理运行结果时，才采用以下示例路径：

```text
results/<项目>/<运行名称>/
├── run.yaml       # 命令、配置、状态及必要上下文
├── train.log      # 或程序原生生成的日志
└── summary.md     # 可选；仅记录有价值的结果与结论
```

如果原生工具已经可靠记录命令、配置和状态，可以不创建 `run.yaml`；不要在多个文件中
重复保存同一信息。运行名称应简短且可辨识，日期不是必需字段。不得覆盖仍有证据价值的
日志和输出。

## 执行流程

1. 阅读项目约束，检查相关 Git 工作区状态并记录所用提交。
2. 优先复用已有脚本和配置；根据任务需要明确运行目的、评价指标或成功条件。
3. 执行前确定结果目录。
4. 按复现风险记录命令、工作目录、代码版本、配置、随机种子、数据与模型版本，以及
   必要的软硬件环境；不得记录凭据、令牌等秘密信息。
5. 保留标准输出、标准错误或程序原生日志，监控时只记录有意义的状态变化。
6. 结束后记录完成、失败或中断状态及主要输出路径。若失败能够解释缺陷、约束或决策，
   应保留相应证据。
7. 只有运行产生了可解释的结果、比较、决策、失败分析或可复用方法时，才写
   `summary.md`。单次运行的事实和结果留在运行目录；跨运行的结论、方法或长期决策再写入
   `research-docs` 管理的权威研究文档，并链接回相关运行记录。

比较不同运行时，应核对指标定义、数据划分、模型版本、关键配置和评测环境是否一致；
存在差异时必须明确说明，不得将不可比结果直接归因于目标变量。

项目仓库的 Git 管理代码；运行记录和输出是否纳入 Git，遵循项目或工作区既有政策。只有明确适合版本控制的小型记录和总结才纳入；原始日志、检查点、模型权重、缓存和大型数据默认不纳入，除非项目已有明确约定。未经用户要求不要提交。

清理前先列出准确目标并确认是否含有不可替代的证据；删除实质性材料必须取得用户明确
同意。

默认不创建活动、实验登记表、实验编号、独立计划、时间线或成套报告。只有用户明确要求，
或运行数量已经造成实际检索困难时，才增加必要结构。
