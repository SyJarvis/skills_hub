# 研究文档管理

文档用于保存可追溯、可复用的知识，而不是复制工作区状态或记录每一次操作。优先更新
现有权威文档，不为同一内容建立平行版本。

## 存放位置

按以下顺序判断：

1. 项目专属文档放在项目仓库内，并遵循该仓库现有目录和命名约定。
2. 运行日志与输出放在 `results/`，由 `research-experiment` 管理；有价值的运行总结可
   放在运行目录中，也可并入项目文档。
3. 工作区的 `docs/INDEX.md` 只用于项目组合总览。
4. 只有内容确实被多个项目共同使用时，才在工作区 `docs/` 下建立共享文档。

写作前先搜索已有文档，能够更新权威来源时不要新建。除非文档本身按时间组织，例如
工作日志，否则不要仅因日期变化而创建“最新版”“最终版”或重复摘要。

Git 负责保存修订历史。除非仓库已经采用相关规范，或用户明确要求，否则不建立中央目录、
文档编号、统一的 YAML 元数据头或人工维护的版本记录。

## 工作流程

1. 阅读 `AGENTS.md`、`CLAUDE.md` 及相邻文档，确认项目约束和写作语境。
2. 判断信息应更新现有文档、建立新文档、写入运行记录，还是无需长期保存。
3. 根据内容需要说明目的与范围、方法、证据、观察、推断、结论和局限；不强制套用固定
   章节。应明确区分直接观察、基于证据的推断和最终决策。
4. 为关键事实和结果提供可追溯来源，链接相关代码、运行结果、数据集或文献，不复制
   可以通过链接获得的大段内容。
5. 检查差异，删除重复表述、无依据结论和不必要的管理性文字。

不为每次运行单独写文档。只有运行产生了有效结果、决策、失败分析或可复用方法时，
才值得保存总结。

内容更新后由 Git 保存旧版本，不另建归档副本。只有归档能够改善检索时才归档；删除
文档必须取得用户明确同意。默认不建立 `docs/knowledge/`、`catalog/documents.yaml`、
逐文档元数据或项目状态副本，除非实际规模或用户要求证明这些结构确有必要。
